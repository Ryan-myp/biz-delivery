# Grill for TD — 技术方案前的自动 grill gate

## 概述

在 ad-dev 的 `PRD → prd-review → TD` 流程中，在 prd-review 之后、TD 生成之前插入一个 **grill gate**。

**核心原则：**
- 没有明确确认的关键设计点，不直接写 TD
- 每次只问一个问题，给出推荐答案
- 如果代码库里有确凿证据（通过 ad-knowledge-query 查询），直接查代码，不提问
- 所有问题在同一个 session 内完成，不阻塞用户其他工作

## 触发条件

当 ad-dev 接收到 PRD 链接/文本，且：
1. 已完成 `prd-review`（或等价的需求澄清）
2. **但** TD 生成所需的关键设计点存在以下任一情况：
   - 数据模型未明确（新增表 vs 扩旧表）
   - 性能指标缺失（QPS、延迟、数据量）
   - 边界条件模糊（失败处理、回滚策略、灰度）
   - 已有实现不明确（代码证据缺失或冲突）
   - 依赖关系不清（上游/下游服务）

**不触发 grill 的情况：**
- PRD 已经非常清晰，所有关键设计点都有明确答案
- 用户显式要求"直接写 TD，不用问"
- 这是一个增量小改动（改 1-2 个字段），不涉及架构变化

## 流程

### 1. 识别模糊点

在 prd-review 之后，ad-dev 先做一轮"gap analysis"：

```
PRD + prd-review 结果
    │
    ▼
对 TD 模板的每个必填章节，检查信息完整性：
  │  1.1 背景与目标 → 已有 ✅
  │  1.2 当前能力与路线 → 查代码（ad-knowledge-query）
  │  1.3 范围边界 → 可能模糊 ❓
  │  2.1 核心功能 → 已有（来自 PRD）
  │  3.x 架构 → 关键决策点 ❓
  │  5.x 数据模型 → 关键 ❓（新增/扩旧/索引）
  │  6.x 接口 → 可能模糊 ❓
  │  7.x 监控 → 可能模糊 ❓
  │  8.x 风险/待确认 → 由 grill 产出的答案填充
    │
    ▼
输出: 问题列表 (Q1, Q2, ... Qn)
```

### 2. 执行 grill

**规则：**
- 每次只问一个问题
- 每个问题附带 **推荐答案**（基于代码证据和最佳实践）
- 用户可以选择：接受推荐、修改推荐、说"你看着办"
- 如果某问题的答案能直接查代码得到，**先查代码，再问**

### 3. 生成 TD

带着 grill 阶段收集的完整答案，按 ad-dev 的 TD 模板生成技术方案。

## 问题分类与推荐答案策略

### 数据模型类

| 问题 | 推荐答案策略 |
|---|---|
| 新增表还是扩旧表？ | 检查 query_knowledge 返回的 schema 证据；如果 PRD 要求新对象关系，推荐新建表族 |
| 是否需索引？ | 根据查询模式推荐；高频查询字段加索引 |
| 是否需兼容旧数据？ | 推荐增量迁移方案，不影响线上 |

### 性能类

| 问题 | 推荐答案策略 |
|---|---|
| 预期 QPS？ | 如果 PRD 没给，根据场景推荐：后台管理 < 100, 前端接口 1k-10k, 批量导入 < 10 |
| 延迟要求？ | 同步接口 < 200ms, 异步接口 < 5s |
| 数据量级？ | 根据历史数据或 PRD 推测，推荐水平分表/归档策略 |

### 边界类

| 问题 | 推荐答案策略 |
|---|---|
| 失败处理？ | 推荐：记录错误 + 告警 + 可重试 + 人工介入入口 |
| 回滚策略？ | 推荐：DB 变更向前兼容，代码变更可灰度 |
| 灰度/分批？ | 推荐：先小流量（1%），观察 24h 后全量 |

### 依赖类

| 问题 | 推荐答案策略 |
|---|---|
| 上游服务改动？ | 检查 ad-knowledge-query 的 callchain 结果 |
| 下游消费方？ | 推荐：向后兼容，新字段可选 |
| 跨服务调用？ | 推荐：RPC 而非 HTTP，加超时和熔断 |

## 用户交互示例

```
## 🎯 技术方案前确认（grill gate）

基于 PRD 和 prd-review 结果，我识别到以下 3 个关键设计点需要你确认：

### Q1/3：数据模型 — 新增表还是扩旧表？

PRD 提到需要新的规则关系模型，但当前 DAP 有旧 rule 表族。

**推荐答案：新建规则表族（Rule Header / Batch / Object / Action / Condition），旧表只读兼容。**

理由：
- 旧表语义不明确，无法稳定表达新关系
- 新表族隔离后便于后续结果回放和历史追溯
- 执行链路（扫描、worker、日志）可复用
```

## 与 ad-dev 的集成

ad-dev 流程：`PRD → prd-review → [grill gate] → TD → 开发计划 → Codex handoff`

步骤 2.5：grill gate — 完成 prd-review 后，先做 gap analysis，识别关键设计模糊点，逐条问用户（每次一个问题 + 推荐答案），代码有据则直接查，所有问题确认后进入 TD 生成。

## Pitfalls

- **不要 grill 过度**：如果 PRD 已经非常清晰，或者用户说"直接写"，跳过 grill
- **推荐答案要有依据**：不要凭空给推荐，基于代码证据或最佳实践
- **一个问题一个问**：不要一次性列出所有问题让用户填问卷
- **可跳过的问题直接查代码**：如果 ad-knowledge-query 有确凿证据，不浪费用户时间
- **grill 结果要可追溯**：每个确认的答案都要记录，TD 中引用"根据 Q2 确认..."
